# Решения и допущения

## Что я решил сам там, где ТЗ не даёт однозначного ответа

1. **Удаление задач мягкое.** ТЗ разрешает удалять задачи и запрещает удалять историю через API.
   Обычное каскадное удаление нарушило бы второе требование, поэтому задача получает отметку об
   удалении и скрывается, а строка и история остаются. Удалённую задачу нельзя восстановить из
   интерфейса: только администратор через базу.
2. **Объект с задачами удалить нельзя.** Сначала нужно удалить его задачи. Это защищает от случайной
   потери работы. Объекты удаляются тоже мягко.
3. **Статус меняется только через функцию базы.** Права на запись в колонку `status` нет ни у кого:
   это исключает обход правил, а история пишется в той же транзакции, что и смена статуса.
4. **Принимать и возвращать может любой постановщик,** а не только автор задачи: ТЗ говорит
   «постановщик».
5. **Исполнитель обязателен при создании задачи.** Статус «Новая» подразумевает, что есть назначенный
   исполнитель, который может взять её в работу.
6. **Исполнителем можно назначить только пользователя с ролью исполнителя.** Иначе задача зависла бы:
   постановщик не может брать задачи в работу. Проверка выполняется в базе.
7. **Принятая задача финальна.** Её нельзя редактировать, можно только удалить.
8. **Постановщик может сменить исполнителя и данные задачи в любом статусе, кроме «Принята».** Прежний
   исполнитель сразу теряет доступ к задаче. Смена исполнителя и правки полей в историю не пишутся:
   по ТЗ история фиксирует только смену статуса.
9. **Создание задачи тоже есть в истории** как первая запись «— → Новая», это строка из таблицы
   переходов в ТЗ.
10. **В интерфейсе комментарий спрашиваем только при возврате на доработку.** База принимает
    необязательный комментарий и для остальных переходов, поле можно добавить без изменения схемы.
11. **Роль хранится в таблице `profiles`, запись в которую через API закрыта,** а не в метаданных
    пользователя: их пользователь может менять сам. Аккаунт без профиля не видит ничего.
12. **Исполнитель видит только имена людей, связанных с его задачами,** а не весь список сотрудников.
    Почта в профилях не хранится.
13. **Удалить пользователя с задачами или историей нельзя:** база не даст, чтобы история не потеряла
    автора.

## Что добавил сверх ТЗ

- Экран задач есть и у постановщика: все задачи с фильтром по статусу, иначе задачи на проверке
  пришлось бы искать по объектам.
- Адаптивная вёрстка для телефона и тёмная тема.
- `npm run security-check`: автопроверка защиты в обход интерфейса.

## Что не успел или сознательно не делал

- Управление пользователями в интерфейсе: по ТЗ их создают вручную в Supabase.
- Автотесты интерфейса: ручной чек-лист в `docs/MANUAL_TEST_CHECKLIST.md`.
- Пагинация списков: для объёма тестового не нужна.
- Перенос задачи на другой объект в интерфейсе: база это допускает, форма нет.
- Обновление в реальном времени: новые статусы видны после перехода или обновления страницы.

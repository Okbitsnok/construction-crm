# Мини-CRM «Объекты и задачи»

Постановщик ставит задачи по стройкам, исполнители выполняют их и отдают на проверку.

**Стек:** Next.js 16 (App Router), React 19, TypeScript, MUI 7, Supabase (Postgres, Auth, RLS).

## Почему такой стек

| Технология | Что даёт в этом проекте |
| --- | --- |
| **Supabase (Postgres + RLS)** | Правила доступа живут в самой базе и действуют при любом обращении, а не только через интерфейс. Вход по email готов из коробки, отдельный бэкенд не нужен |
| **Next.js (App Router)** | Страницы загружают данные на сервере от имени пользователя, а гостя перенаправляют на вход ещё до отрисовки. Server Actions заменяют ручной слой API: меньше кода и мест для ошибок. Просто деплоить на Vercel |
| **MUI** | Готовые доступные компоненты: диалоги, формы, адаптивность, тёмная тема. Время уходит на логику и защиту, а не на вёрстку базовых элементов |
| **TypeScript** | Типы таблиц и запросов: ошибка в имени поля или статусе видна при сборке, а не у пользователя |
| **React Hook Form** | Формы и проверка полей без лишнего кода. Окончательную проверку всё равно делает база |

**Компромисс:** серверный рендеринг не обязателен для внутренней CRM, тот же результат дал бы и
React на Vite. Next выбран за защиту маршрутов на сервере, меньший объём кода и потому что я на нём
быстрее и надёжнее всего работаю.

## Запуск

1. Создайте проект Supabase и выключите регистрацию:
   Authentication → Sign In / Providers → **Allow new users to sign up**.
2. Примените миграции из `supabase/migrations` по порядку: `npx supabase link`, затем
   `npx supabase db push`, либо вставьте файлы в SQL Editor.
3. Создайте пользователей в Authentication → Users → Add user (Auto Confirm):
   `manager@mini-crm.test`, `manager2@mini-crm.test`, `ivanov@mini-crm.test`, `petrov@mini-crm.test`.
4. Выполните `supabase/seed.sql` в SQL Editor: он назначит роли и добавит демо-данные.
5. Запустите приложение:

   ```bash
   cp .env.example .env.local   # заполнить значения из Project Settings → API Keys
   npm ci
   npm run dev
   ```

## Проверка защиты

```bash
npm run security-check
```

Скрипт обращается к Supabase напрямую, в обход интерфейса: с публичным ключом, под гостем и
реальными пользователями. Он пробует запрещённые действия и показывает, какие заблокированы.
После работы скрипта остаются служебные записи «Тест защиты», скрытые мягким удалением.

Остальные команды: `npm run typecheck`, `npm run lint`, `npm run build`.

## Как устроена защита

| Требование | Где реализовано |
| --- | --- |
| Исполнитель видит только свои задачи и объекты | RLS-политики, `20261106000200_access_control.sql` |
| Статус нельзя сменить напрямую | Права на колонки: у API нет записи в `status` |
| Запрещённый переход не пройдёт | Функция `change_task_status` и таблица `private.task_transitions` |
| Историю нельзя подделать или удалить | У API только чтение; триггеры запрещают изменение и удаление всем ролям |
| Удаление не стирает историю | Мягкое удаление: `delete_task`, `delete_object` |
| Секреты не попадают во фронтенд | Приложение использует только публичный ключ, `service_role` не нужен |

Кнопки действий приходят из базы (`get_available_transitions`), поэтому интерфейс не дублирует
правила переходов.

## Структура

```text
supabase/migrations   схема, права, логика статусов
supabase/seed.sql     демо-данные
scripts/              автопроверка защиты
src/app               страницы (Server Components загружают данные)
src/shared            запросы, Server Actions, клиенты Supabase
src/components        общие компоненты интерфейса
src/materialUI        тема MUI
docs/                 объяснение для руководителя, решения и допущения
```
